# Zimika Video Flow 前期准备说明

这份说明用于首次部署、引擎更新或环境排查时确认机器、TTS 服务商和 Remotion 环境。对外只提供一个 `shin-video` 入口；内部模块不需要单独安装或调用。

## 一、工作流基础

Zimika Video Flow 是文章口播驱动的视频生成工作流：

```text
文章内容
→ 文本模型生成口播文案
→ TTS 服务商同时生成最终音频和原生时间戳
→ Agent 生成字幕、场景、素材清单和导演方案
→ Remotion 按导演方案渲染视频
```

核心分工：

| 模块 | 作用 |
|---|---|
| 文本模型 | 整理文章并生成自然口播 |
| TTS 服务商 | 同次生成 `口播音频.mp3` 和原生时间戳 |
| Agent | 生成制作 Brief、字幕、场景、素材、导演方案和视觉配置 |
| Remotion | 按时间轴、音频和导演配置渲染视频 |
| FFmpeg | 支撑编码和基础音视频检查 |

## 二、用户需要提供什么

至少提供：

```text
1. 文章正文、文章文件或文章链接
2. 可用的 TTS 服务商配置
3. 对口播文案和画面方向的确认
```

如果用户提供已有音频，还必须同时提供同次 TTS 请求返回的原生时间戳。只有音频不能进入正式场景和渲染链路。

## 三、机器环境

必须具备：

```text
Node.js
npm
FFmpeg
Remotion
Zimika Video Flow Remotion 模板
至少一个支持原生时间戳的 TTS 服务商
```

首次部署、引擎更新或环境排查时检查：

```bash
node -v
npm -v
ffmpeg -version
npx remotion --version
npm run doctor
```

macOS 安装基础环境：

```bash
brew install node ffmpeg
```

在项目根目录安装依赖：

```bash
npm install
```

## 四、TTS 服务商

### MiniMax

```text
MINIMAX_API_KEY
MINIMAX_TTS_ENDPOINT=https://api.minimax.chat/v1/t2a_v2
MINIMAX_TTS_MODEL=speech-2.8-hd
MINIMAX_VOICE_ID
MINIMAX_GROUP_ID（可选）
```

### 火山引擎

```text
VOLCENGINE_TTS_API_KEY
VOLCENGINE_TTS_ENDPOINT
VOLCENGINE_TTS_RESOURCE_ID=seed-tts-2.0
VOLCENGINE_TTS_VOICE_ID=zh_female_xiaohe_uranus_bigtts
```

### 其他服务商

自定义接入必须明确：

```text
接口地址
鉴权方式
模型
音色
音频返回格式
原生时间戳返回格式
```

不返回原生时间戳的接口不能用于当前正式链路。

## 五、时间轴合同

TTS 调用后必须同时保存：

```text
口播音频.mp3
RUN_DIR/subtitle-timeline.json
```

时间轴至少应能证明：

```text
source 为 provider-native
来自哪一个服务商和请求
对应哪一个音频指纹
对应哪一版口播文案指纹
每段 start/end 合法且有序
整体覆盖最终音频有效时长
```

字幕正文固定从 `口播文案.md` 读取。服务商返回文本只用于时间校验，不得覆盖字幕。

口播文案、音频、音色、模型、服务商或请求变化后，旧时间轴立即失效。

## 六、Remotion 环境

进入完整项目目录：

```bash
npm install
npx remotion --version
npm run doctor
```

正式项目必须包含：

```text
Remotion 入口
Zimika Video Flow 视频模板
remotion/visual-library
导演镜头类型映射
字幕安全区
运行时 JSON 读取合同
```

仅安装 Remotion CLI 不代表已经具备完整 Zimika Video Flow 渲染能力。

## 七、项目结构

```text
视频项目/
├── 文章正文.md
├── 口播文案.md
├── 口播音频.mp3
├── _runtime/
│   └── <run-id>/
│       ├── video-brief.json
│       ├── subtitle-timeline.json
│       ├── scenes.json
│       ├── asset-manifest.json
│       ├── visual-manifest.json
│       ├── director-plan.json
│       └── style-profile.json
└── <视频标题>.mp4
```

中间文件统一放在 `<项目目录>/_runtime/<run-id>/`，最终成片统一放在
`<项目目录>/<视频标题>.mp4`。

## 八、开始前检查

- [ ] 能读取文章或链接
- [ ] 能生成 `文章正文.md`
- [ ] 能生成纯净 `口播文案.md`
- [ ] 已配置支持原生时间戳的 TTS 服务商
- [ ] TTS 能同时输出音频和时间戳
- [ ] `RUN_DIR/subtitle-timeline.json` 的 `source` 为 `provider-native`
- [ ] 音频和文案指纹与时间轴一致
- [ ] Node.js、npm 和 FFmpeg 可用
- [ ] Remotion 依赖可用
- [ ] 首次部署、引擎更新或环境排查时，`npm run doctor` 通过
- [ ] Zimika Video Flow 模板和视觉组件库存在

## 九、禁止事项

- 不得只有音频就继续制作。
- 不得使用非同次 TTS 返回或无法验证来源的时间位置。
- 不得让服务商返回文本覆盖确认后的口播文案。
- 不得把画面提示、分镜或时间码写入口播文案。
- 不得跳过素材清单、导演方案和生产门槛。
- 不得把只有 Skill 文档、缺少 Remotion 模板的安装描述成完整版本。
- 不得把真实密钥写入公开文件。
- 不得把 `npm run doctor`、测试、构建或工作流验证塞进每条视频的日常制作流程。

## 十、一句话说明

```text
Zimika Video Flow 使用文本模型生成口播，由 TTS 服务商同时提供最终音频和原生时间戳，再通过导演系统与 Remotion 组件库生成带字幕、素材和动态视觉的视频。
```
